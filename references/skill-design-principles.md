# Skill 设计原则

> 来源：agentskills 官方 best-practices 指南 + 本工坊沉淀。设计新技能或重构旧技能时先读本文件。

## 1. 从真实经验出发，不靠通用知识

最常见的坑：让 LLM 凭空生成技能，得到的是"处理错误"、"遵循认证最佳实践"这类空话。

正确做法二选一：

- **从一次真实任务中提取**：在对话里完成一次真实任务（含你的纠正、补充的上下文、输入输出格式），然后把可复用模式抽出来。
  - 哪些步骤**有效**；
  - 你在哪里**纠正**过它（"用库 X 不用库 Y"、"注意边界情况 Z"）；
  - 输入/输出**长什么样**；
  - 你提供了哪些它本来不知道的**项目事实**。
- **从现有工件中综合**：用团队真实的 runbook、事故报告、schema、评审意见、补丁历史喂给模型综合成技能——比通用教程强得多。

## 2. 用真实执行打磨

初稿通常需要打磨。对真实任务跑一遍，把**全部结果**（不只失败）喂回创作流程，问三个问题：哪些是误触发？哪些漏了？哪些可以砍？

读**执行轨迹**而不只看最终输出：智能体在无用步骤上绕圈，通常是因为指令太模糊、指令不适用于当前任务、或选项太多没有默认值。

## 3. 上下文是公共资源

技能激活后整份 SKILL.md 进入上下文，与历史、系统上下文和其他技能竞争注意力。

- **只加智能体缺的，砍掉它知道的**。判断标准："没有这条指令，智能体会不会做错？"不会 → 砍。
- 如果智能体没有这个技能也能干好整个任务，这技能就没有价值。

## 4. 内聚单元

像设计函数一样设计技能：**一个技能封装一个连贯的工作单元**。
- 太窄：一次任务要加载多个技能，增加开销和指令冲突；
- 太宽：难以精确触发（"查询数据库并格式化结果"是内聚的，"还要管数据库运维"就过界了）。

## 5. 细节颗粒度适中

过度全面反而有害：智能体难以提取相关内容，可能沿不适用的指令走弯路。简洁的分步指引 + 一个能跑的示例 > 穷尽式文档。别试图覆盖所有边界情况——多数交给智能体自己的判断。

## 6. 控制颗粒度匹配任务脆弱性

| 场景 | 写法 |
|---|---|
| 多种方法皆可、容忍变化 | 给自由，解释"为什么"比硬性规定有效 |
| 脆弱、一致性关键、顺序必须固定 | 精确到命令，明确"不要改" |
| 多数技能是混合体 | 各部分独立校准 |

## 7. 给默认值，不给菜单

多工具可选时：**选一个默认，简单提一句备选**，不要把备选并列展示。

## 8. 教程序，不教声明

技能教"如何处理一类问题"，不是"这个具体实例怎么做"。

- 声明：`把 orders 表 join customers 表，filter 掉 region='EMEA'，sum amount`
- 程序：`1. 读 references/schema.yaml 找相关表 → 2. 按 _id 外键约定 join → 3. 把用户请求的筛选写成 WHERE → 4. 聚合并格式化`

特定细节（输出格式模板、"绝不输出 PII"约束、工具特有指令）仍然有价值，但**方法要能泛化**。

## 9. Gotchas 章节（最高价值内容）

环境特异、反直觉的事实清单——"不告诉就会错"的修正：

```
## Gotchas
- users 表是软删除，查询必须带 WHERE deleted_at IS NULL
- user_id / uid / accountId 三者是同一个东西，只是不同服务叫法不同
- /health 只要 web 服务活着就返回 200，即使数据库挂了；看 /ready
```

**每当用户纠正你一次，就把修正写进 Gotchas**——这是迭代最直接的输入。

## 10. 输出格式模板

需要固定输出格式时给模板，别用散文描述。短模板内联进 SKILL.md；长模板或按需加载的放 `assets/` 并引用。

## 11. 多步流程清单

有依赖或校验门槛的流程，用显式清单帮智能体跟踪进度、防跳步：

```
- [ ] Step 1: 分析表单（跑 scripts/analyze_form.py）
- [ ] Step 2: 建字段映射
- [ ] Step 3: 校验映射（跑 scripts/validate_fields.py）
- [ ] Step 4: 填表
- [ ] Step 5: 验证输出
```

## 12. 验证回路（Validation Loops）

"做完 → 跑校验 → 出错就修 → 再校验 → 全绿才继续"。校验器可以是脚本，也可以是参考文档清单。

## 13. Plan-Validate-Execute

批量或破坏性操作：先产出结构化计划 → 用源头校验计划 → 再执行。关键在"第 3 步"：校验脚本把计划与源头对比，错误信息要给足可自纠正的细节（"字段 signature_date 不存在——可用字段：…"）。

## 14. 脚本打包信号

反复跑测试用例时，如果发现智能体每次都在**重新发明同一个逻辑**（建图、解析格式、校验输出），就把逻辑写成测过的脚本打包进 `scripts/`。

## 15. 渐进式披露

主 SKILL.md ≤500 行 / ≤5000 token，只放每次运行都要的核心指令；长资料拆到 references，并**明确告诉智能体什么时候读哪个文件**："API 返回非 200 时读 references/api-errors.md"，而不是"细节见 references"。
