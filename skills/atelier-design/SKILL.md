# atelier-design · 设计

把发现阶段的候选（或用户指定的目标）变成一份可执行的设计文档。**不创建任何文件**，产出的设计文档放 `profile.yml` 的 `directories.drafts`。

## 何时使用

- `/atelier design <目标>`；
- 候选报告建议"新建"，动手制造前；
- 重构既有技能前需要明确责任边界。

## 流程

1. **收集使用例子**：问清或从记录里找出 2–3 个真实使用场景（触发的话术、输入、期望输出）。不清楚就问，一次别问太多。
2. **推演执行路径**：对每个例子从零推演一遍，识别可沉淀资源：
   - 反复重写、需确定性 → `scripts/`；
   - 每次都要重新查的文档/模式 → `references/`；
   - 产出需要的模板/样板 → `assets/`。
3. **写设计文档**，逐项覆盖：
   - 精确能力边界（做什么）；
   - 非目标（明确不做什么）；
   - 输入契约（必需参数/文件/前置条件）；
   - 输出契约（产出物与格式，按 profile.yml 的 preferred_tools）；
   - 权限与运行时依赖（网络、系统包、需确认的高风险操作）；
   - 触发条件（描述怎么写）；
   - 失败行为（出错时回退路径与报告）；
   - 验收标准（可测试、可验证的完成定义）。
4. **对照自检**：过一遍 `../../references/skill-design-principles.md`，确认边界内聚、颗粒度适中、给默认值不给菜单、教程序不教声明。

## 设计文档模板

```
# <name> 设计文档
能力边界：…
非目标：…
输入契约：…
输出契约：…
权限与依赖：…
触发条件（description 草案）：…
失败行为：…
验收标准：
- [ ] 触发：…（描述能命中哪些真实请求）
- [ ] 运行：…（关键脚本/步骤可执行）
- [ ] 边界：…（非目标场景不会误触发）
资源规划：scripts/… references/… assets/…
```

## 非目标

- 不创建目录/文件（那是 atelier-build）；
- 不做触发测试（那是 atelier-validate）；
- 不评估值不值得做（那是 atelier-discover）。

## Gotchas

- 设计里出现"处理错误""遵循最佳实践"这类空话 → 重写，它说明你缺真实上下文；
- 边界写不窄 = 触发会乱，回炉；
- 验收标准必须可测："能跑"不算，"跑出预期输出且 exit 0"才算。
